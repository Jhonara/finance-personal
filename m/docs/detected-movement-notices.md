# Avisos locales de movimientos detectados

## Funcionamiento

- En Android, texto compartido, imagen y PDF se interpretan en el dispositivo. Solo los campos sugeridos se envían a `POST /inbox` con una clave estable. Cada página de un PDF usa una clave distinta. El backend conserva su idempotencia y el ledger no cambia hasta la confirmación expresa.
- El lector opcional de avisos bancarios mantiene su cola cifrada y aislada por usuario. Con la aplicación activa, se sincroniza al abrirla, al volver a primer plano y cada 15 segundos. Solo se retira un aviso de la cola después de recibir un pendiente del servidor.
- Después de recibir el ID del pendiente, `expo-notifications` puede publicar un aviso en el canal Android **Movimientos detectados**. Su permiso para mostrar avisos es independiente del permiso de Android para leer avisos de otras apps. El lector excluye el paquete de Finance Personal para evitar ciclos.
- Los avisos están desactivados por defecto. Importe y comercio permanecen ocultos hasta que cada opción se active en Perfil y ajustes. El canal usa visibilidad privada en la pantalla bloqueada. El contenido nunca incluye texto original, credenciales, tokens, cuentas o tarjetas.
- El ID del pendiente, no el importe ni el comercio, determina si ya se intentó emitir el aviso inicial. La marca se guarda por usuario antes de programarlo para evitar duplicaciones después de un cierre abrupto. Si falla la programación después de esa marca, puede faltar un aviso, pero el pendiente permanece en la bandeja.
- Al tocar un aviso, se conserva el ID objetivo y se verifica `/me` y `GET /inbox/{id}` antes de abrir el detalle. Si vence la sesión, se solicita login y se retoma el objetivo solo si vuelve a entrar su propietario. Un usuario distinto nunca recibe el detalle de otro.
- Confirmar, vincular o descartar intenta quitar el aviso visible. Cerrar sesión elimina los avisos visibles y los programados. Las preferencias y marcas de deduplicación se guardan por usuario en SecureStore.

## Límite conocido

`expo-notifications` programa avisos desde JavaScript. Si Android mantiene únicamente el `NotificationListenerService` mientras la app está cerrada, el lector puede guardar un candidato local cifrado, pero no puede crear un pendiente en Spring Boot ni emitir una notificación de Expo con su ID de servidor hasta que se reactive la app y se verifique la sesión. No se inventa un ID ni se registra un gasto. Para avisar inmediatamente en ese estado haría falta una cola nativa con aviso propio y una ruta de reconciliación de IDs al reabrir, o un trabajo nativo autenticado con una política explícita de credenciales. Esto requiere una etapa de arquitectura y pruebas de seguridad aparte.

Dos comprobantes con igual importe y comercio se separan cuando tienen eventos o contenidos distintos. Si dos comprobantes son byte por byte idénticos y la fuente no da identificador de evento, ningún lector puede demostrar por sí solo que representan compras diferentes; la revisión manual sigue disponible.

## Pruebas reproducibles en Android

1. Instalar el APK de desarrollo, abrir la app e iniciar sesión. En Perfil y ajustes, activar **Avisos de movimientos detectados** y aceptar el permiso de Android. Comprobar que importe y comercio están apagados.
2. En Movimientos detectados, compartir un texto de prueba como `Compraste COP 12.500 en Comercio QA el 27/10/2026` o leer una imagen/PDF de prueba. Verificar un único pendiente y una única notificación sin importe. Pulsarla: debe abrir su detalle. Descartar el pendiente y comprobar que el saldo no cambia.
3. Repetir el mismo comprobante: no debe aparecer un segundo pendiente ni una segunda notificación inicial. Usar dos avisos bancarios distintos con igual importe y comercio pero diferente hora de publicación: deben quedar dos pendientes separados.
4. Denegar el permiso para **mostrar** avisos y repetir la captura: debe guardarse el pendiente sin notificación. No confundirlo con el permiso separado para **leer** avisos bancarios.
5. Cortar internet antes de guardar: la captura debe permanecer visible y ofrecer **Reintentar guardado**. Restaurar la red, reintentar y verificar un solo pendiente.
6. Tocar una notificación con sesión vencida; tras autenticar al mismo usuario debe abrirse su detalle. Entrar con otro usuario debe ocultar ese detalle y los avisos anteriores.
7. En segundo plano, compartir un comprobante y comprobar el aviso. Con la app cerrada, comprobar que un aviso bancario autorizado se conserva en la cola y se sincroniza al reabrir; la notificación inmediata con la app cerrada sigue siendo el límite descrito arriba.

No ejecutar **Confirmar gasto** con datos ficticios en una cuenta real: esa acción sí modifica el ledger.

## Validación realizada

- `npm test -- --no-file-parallelism`: 73 archivos y 634 pruebas aprobadas. La ejecución paralela falló en dos suites de interfaz por carga del entorno; esas suites pasaron aisladamente y la batería completa pasó en secuencia.
- `npm run typecheck`, `npm run lint` y `npm run format:check`: aprobados.
- Android: el módulo Kotlin compiló, EAS entregó un APK de desarrollo y `adb install -r` lo instaló sin borrar datos. `aapt` confirmó `android.permission.POST_NOTIFICATIONS` en ese APK.
- EAS compiló un APK autónomo con el perfil `widget-qa`, pero ese perfil apunta al servidor ficticio del widget (puerto 8095) y no sirve para entrar con la cuenta de Spring Boot. Otro APK autónomo con `detected-qa` apuntó al puerto correcto (8080), pero Android bloqueó su HTTP porque la excepción de red solo cubría el perfil anterior. Se corrigió el config plugin para ambos perfiles de emulador; una nueva compilación EAS quedó bloqueada por la cuota mensual, que se restablece el 1 de noviembre de 2026. El perfil normal no habilita HTTP sin cifrar.
- Para continuar sin otro build EAS, se instaló el [APK de desarrollo Android](https://expo.dev/accounts/jhonara/projects/finance-personal-mobile/builds/b2a8dbb6-29ae-4302-9cb2-d6d342bfb42e) y se cargó Metro con la URL del backend del emulador. Se inició sesión con la cuenta de prueba y se comprobó que Inicio mostraba datos del servidor. En Perfil y ajustes se activaron los avisos; Android pidió por separado permiso para **mostrar** notificaciones, que se concedió. Se comprobaron el canal `detected-movements` y que importe y comercio permanecían ocultos.
- Un texto compartido de prueba fue interpretado como compra con importe, pero `POST /inbox` devolvió 500 y no creó el pendiente ni la notificación. Una llamada directa aisló la causa: la restricción de la base de datos aún solo admitía las cuatro fuentes anteriores. Se añadió `V22__purchase_draft_capture_sources.sql` para permitir `SHARED_TEXT`, `IMAGE`, `PDF` y `NOTIFICATION`. La prueba de migración acepta todas las fuentes conocidas y rechaza una desconocida. Después del reinicio de Spring Boot, la captura se repitió correctamente en el emulador.
- **Emulador, app abierta:** un texto compartido ficticio creó un pendiente con fuente `SHARED_TEXT` y un aviso local genérico en el canal `detected-movements`. `dumpsys notification` mostró visibilidad privada; el título y el cuerpo no incluyeron importe ni comercio. Al tocar el aviso se abrió el detalle de ese mismo pendiente, todavía sin cuenta ni categoría y sin poder confirmar el gasto.
- **Idempotencia:** compartir otra vez el texto idéntico mantuvo un solo pendiente y no volvió a publicar el aviso inicial. Compartir otro texto ficticio con el mismo importe y comercio, pero distinta hora, creó un segundo pendiente. El segundo aviso se tocó con la app en segundo plano y abrió el segundo detalle. La interfaz señaló la posible coincidencia para revisión.
- **Descarte e integridad:** ambos pendientes se descartaron desde su pantalla de revisión. La API devolvió cero pendientes; el historial mostró los dos como `DISCARDED`. La suma de saldos COP del resumen del servidor coincidió con el valor anterior a la prueba.
- **Permiso denegado:** se revocó temporalmente `POST_NOTIFICATIONS`, se compartió un tercer comprobante ficticio y la app creó su pendiente sin publicar un aviso. Se descartó desde la interfaz, la API volvió a mostrar cero pendientes y el saldo permaneció igual. Después se restauró el permiso Android.
- **Pruebas automatizadas:** cubren permiso denegado, aviso único por pendiente, dos compras con igual importe/comercio e identidad distinta, aislamiento por usuario, sesión vencida, pérdida de conexión y navegación diferida. El backend pasó `PurchaseDraftCaptureSourceMigrationTest` (1 prueba) e `InboxIntegrationTest` (19 pruebas).

**Pendiente de validación real:** ingreso desde imagen/PDF o lector de avisos bancarios, proceso cerrado antes de sincronizar, sesión vencida, cambio de usuario, pérdida y recuperación de conexión, y confirmación contable con una operación de prueba reversible. La app cerrada conserva el límite arquitectónico descrito arriba. La compilación local de release en Windows falló por la longitud de rutas CMake de dependencias nativas; el APK de desarrollo permitió validar interfaz, servidor y notificaciones, pero el APK autónomo corregido no se ha compilado por la cuota EAS agotada hasta el 1 de noviembre de 2026.
